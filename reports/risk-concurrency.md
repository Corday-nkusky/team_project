# 高风险三查 · 并发

## 用什么手段查

通过真实 HTTP 接口同时发出两个上传请求，收齐响应后用独立 MySQL 查询和 Qdrant 精确计数核对结果。脚本为 `scripts/async-criteria.mjs`。专用入口保持 worker 在线，使用随机标题与一份单切片正文，结束时清理测试材料。

## 查了什么

同一位教师向本班并发上传完全相同的材料。记录两个请求从开始到收齐响应的在途重叠时长，随即核对响应标识，再等该任务成功完成。重叠时长是客户端观测值，数据库持久化结果单独核验。

## 通过判据

两个请求在途时间重叠，均返回 HTTP 202、相同的有效材料 ID 和任务 ID。按本班及唯一标题查询材料、关联上传任务各一行；任务关联此次材料并成功完成；该材料仅有一条切片、一个唯一序号和一个向量点。任何一步不满足则专用入口退出非零。

## 实测与复跑

2026-11-20，两次请求在途重叠 5.04 ms，均返回材料 18、任务 `05d137dee47f6753f1f0a2b6ea8511e8`。实际材料、上传任务、切片、向量点分别为 1、1、1、1，退出 0。[原始结果与计数查询](concurrent-uploads.md)。

前置：启动本仓库 Compose 服务、worker 和可用的嵌入网关。将 BASE 指向同一套容器的 HTTP 地址（下例为实测端口），用该班教师账号运行：

```sh
BASE=http://127.0.0.1:8081 USER=teacher1 node scripts/async-criteria.mjs --criterion concurrent
```

此前 2026-11-17 的[顺序重复提交、重索引和 worker 重投记录](criterion-3.log)保留作独立证据。完整判据三入口 `--criterion 3` 先运行上述并发检查，再验证重索引和重投。
