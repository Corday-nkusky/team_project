# CampusClaw 独立走查报告

日期：2026-10-30 · 基线：`main@031552c` · 测试环境：本机 compose（8080，LLM 关闭）+ 临时 8090 探针实例 + 假模型网关

## 0. 结论先行

这轮没有跑仓库自带的 `cmd/e2e` 或 `e2e-ui.mjs`，而是用三条独立路径重新验证：

1. Node `fetch` 直接调用接口，自己解析 SSE；
2. 起一个假的 OpenAI 兼容网关，制造截断、空流、5xx、超长延迟与伪造引用；
3. 通过浏览器连接器走真实界面，包括文件选择、登录切换、提问、停止。

主流程能跑通：登录、文本上传、索引就绪、命中问答、引用展示、无依据固定文案、班级隔离都正常。

但发现了一个**比原计划所有问题都更伤信任的缺陷**：无依据判定会被「如何 / 都是 / 什么」这类常见双字词击穿。跨领域的问题会被当成“有依据”，返回一段完全无关的材料并附上引用，`no_evidence=false`。这不是模型幻觉，是检索层的判定错误。

按严重度排序：

| 编号 | 级别 | 问题 | 是否在原 14 项内 |
| --- | --- | --- | --- |
| N01 | P0 | 常见双字词即可通过相关性门槛，跨领域问题返回无关材料且标记为有依据 | 否 |
| N02 | P1 | 标题超长 / 非 UTF-8 正文直接 500；UI 无长度约束，255 字标题把表格行撑到 281px | 部分（B03 邻域） |
| N03 | P2 | 模型输出里的 `[9]` 不校验引用清单，原样流式输出并落库 | 否 |
| N04 | P2 | 方法/体积契约不统一：GET→404、PUT→405 纯文本、`Allow` 含 GET/HEAD、1.1MiB→400 而非 413 | 否 |
| N05 | P2 | 严格 JSON 解码缺失：合法对象后面的尾随内容被忽略并照常开始问答 | 否 |
| N06 | P2 | 500 只留访问日志，底层错误没有 ERROR 日志，线上无法定位 | 否（B13 邻域） |
| N07 | P3 | 窄视口下「索引状态」表头与徽标竖排成单字；长标题行高 281px | 否 |

同时修正了原计划里的一处事实错误：**17 MiB 上传不是“静默截断后 201”，而是 500「落库失败」**，因为 `content` 列是 `MEDIUMTEXT`（16 MiB 上限），请求在写入数据库时被拒绝。B03 的修法不能按“去掉静默截断”来写，要按“请求上限与列容量对齐”来写。

## 2. 新发现

### N01（P0）常见双字词击穿无依据判定，答非所问还带引用

**现象**

在 1 班（104 份材料）分别提问：

| 问题 | 系统行为 | 实际引用 |
| --- | --- | --- |
| 贝尔不等式的量子力学推导过程是什么？ | `no_evidence=false`，正常回答 | 《动物行为学｜动物行为学》 |
| 如何在家做红烧肉？ | `no_evidence=false`，正常回答 | 《动物行为学｜动物行为学》《植物学｜花（2/3）》 |
| 法国的首都是哪里？ | `no_evidence=false`，4 条引用 | 《遗传学｜基因（3/3）》《生物化学｜酶（1/3）》等 |

对照组「紫罗兰色的大象在跳舞」反而正确返回「资料中未找到相关内容」。

**根因**

`backend/internal/retrieval/retrieval.go:164` 的 `tokenize` 把**每一个相邻汉字组合**都标成 `strong`，没有停用词表；`backend/internal/qa/qa.go:137-156` 只要 `strongHits > 0` 且 `coverage >= 0.25` 就认定有依据。

用真实切片复算：

| 问题 | 查询强词数 | 最高覆盖 | 命中的词 | 是否过线 |
| --- | --- | --- | --- | --- |
| 贝尔不等式的量子力学推导过程是什么？ | 16 | 0.250 | 式的 / 过程 / 是什 / 什么 | 刚好过线 |
| 如何在家做红烧肉？ | 7 | 0.286 | 如何 / 何在 | 过线 |
| 法国的首都是哪里？ | 7 | 0.429 | 法国 / 国的 / 都是 | 过线 |
| 紫罗兰色的大象在跳舞 | 9 | 0.222 | 色的 / 的大 | 未过线 |

「如何 / 都是 / 什么 / 式的」这些词不携带任何学科信息，却能把覆盖率推过 0.25。紫罗兰那句只是差了一个泛词，说明当前判定边界几乎是随机的。

如果启用了向量路，`byKeyword || byVector` 还会放宽：只要有一个强词命中，向量分 ≥ 0.55 也能成为依据，泛词问题会被进一步放大。

**影响**

核心承诺是“只依据本班材料回答，没依据就明说”。现在用户问一个完全无关的问题，会得到一段看似有出处的错误答案，而且界面没有任何低置信提示。这比“拒答太多”严重得多。

**建议**

1. 建停用词 / 泛词表，至少覆盖：如何、什么、为什么、怎么、哪里、都是、就是、可以、一个、这个、我们、他们、的是、了的、是在、有哪、哪些、多少、是否、以及、因为、所以、但是、如果、然后。
2. 覆盖率改成 IDF 加权：`sum(IDF(命中词)) / sum(IDF(查询词))`，并排除高频泛词；或者要求至少 2 个 `df` 低于语料 5% 的内容词。
3. 向量相似度只用于排序，不单独作为“有依据”的通行证；至少要求关键词侧有内容词命中。
4. 把这三条跨领域问题写成回归用例，断言必须是 `no_evidence=true` 且正文等于固定文案。
5. 用 20 条本班问题 + 20 条跨领域问题做一次小型标注评估，再决定阈值；不要继续凭 0.25 这个魔数。

### N02（P1）标题与正文编码没有边界，直接 500；界面还把长标题渲染成灾难

**现象**

- 标题 256 字 / 300 字：`POST /api/materials` 返回 500 `{"error":{"code":"internal","message":"落库失败"}}`。
- 非 UTF-8 的 `.txt`：同样 500「落库失败」。
- 17 MiB 文本：500「落库失败」，不是 201，也不是截断。
- UI 标题输入框没有 `maxLength`；255 字标题在 524px 视口下把行高撑到 281px（普通行 71px）。
- 500 响应在日志里只有一条 `http_request status=500`，没有底层错误。

**根因**

- 数据库 `materials.title VARCHAR(255)`、`content MEDIUMTEXT`；handler 只做了 `TrimSpace`，没有按 rune 校验长度，也没有 `utf8.Valid` 校验。
- `CreateMaterial` 的错误直接映射成 500，没有区分“输入超限”和“服务故障”。
- 前端没有长度约束，也没有截断/换行策略。

**建议**

- 标题按 rune 限制 ≤255，超限返回 400 + 字段级错误；前端加 `maxLength` 与字数提示。
- 正文先 `utf8.Valid`，非法编码返回 400。
- 请求体上限与列容量对齐：要么把 `content` 改成 `LONGTEXT`，要么把上传上限降到 16 MiB 并在 `.env.example` / 文档 / 错误文案里统一；不要对外说 32 MiB。
- 500 分支用 `slog.Error` 记录 `request_id`、操作、底层错误；响应仍保持通用文案，不泄漏 SQL。

### N03（P2）模型输出 `[9]` 不校验引用清单

**现象**

假网关返回「材料里说的是这样[9]。 另一个结论[1]。」时，后端把整段原样流式输出并落库；实际引用清单只有 1 条。前端会把 `[9]` 渲染成一个引用角标，但引用区没有第 9 条。

**影响**

模型一旦编号越界，用户会看到一个指向不存在来源的引用；如果模型被注入，甚至可以伪造“有出处”的假象。

**建议**

- 生成结束后解析 `[n]`，只保留 1..len(citations) 的编号；越界编号降级为普通文本或替换为最近的合法引用，并记录一条 warn 日志。
- 加一条假网关用例：输出 `[9]` 时，最终回答中不出现无对应引用的角标。

### N04（P2）方法/体积契约不统一

实测：

| 请求 | 实际响应 | 期望 |
| --- | --- | --- |
| `GET /api/ask` | 404 JSON「接口不存在」 | 405 JSON + `Allow: POST` |
| `PUT /api/ask` | 405 `text/plain`，`Allow: GET, HEAD, POST` | 405 JSON + `Allow: POST` |
| 1.1 MiB JSON | 400「请求体格式不正确」 | 413（或 400 但文案说明超限） |
| `Content-Type: text/plain` | 400 | 415 更准确 |

根因是 `router.go` 把 `GET /` 作为 SPA 兜底注册，Go 1.22 的方法路由对未注册方法返回纯文本 405；`Allow` 里混入了 GET/HEAD。

**建议**

- SPA 兜底只处理非 `/api/` 的 GET；`/api/` 未匹配统一走 JSON 404。
- 对已存在路径的未注册方法返回 JSON 405，并写正确的 `Allow`。
- 用 `http.MaxBytesReader` 区分 413；错误体保持统一结构。

### N05（P2）尾随 JSON 被忽略，严格解码缺失

`{"question":"光合作用是什么？"}{"x":1}` 返回 200 并正常开始 SSE。说明解码器只读了第一个对象，没有检查 `dec.More()` / 尾随数据。

**影响**

契约上请求体只允许一个 JSON 对象；接受尾随内容会让代理/网关与后端对同一请求产生不同理解，也给日志与审计留下歧义。

**建议**

解码后检查 `dec.More()`，有尾随内容返回 400。顺带考虑 `DisallowUnknownFields`（如果产品不希望静默忽略拼错的字段）。

---

### N06（P2）500 分支没有底层错误日志

标题 300 字触发 500 后，`docker logs` 只有：

```json
{"level":"INFO","msg":"http_request","method":"POST","path":"/api/materials","status":500}
```

没有 `slog.Error`、没有 SQL 错误、没有 `request_id` 关联的失败原因。线上只能看到“有人失败了”，无法定位是列超长、连接断开还是别的。

**建议**

在 `CreateMaterial` / `SetMaterialStatus` / `SaveConversation` 等错误分支加 `slog.ErrorContext`，字段含 `request_id`、`operation`、`error`；不要把 SQL 语句或敏感值打出来。

### N07（P3）窄视口表格排版退化

524px 视口下：

- 「索引状态」表头竖排成「索 / 引 / 状 / 态」；
- 「可检索」徽标竖排成「可 / 检 / 索」；
- 255 字标题行高 281px，是普通行的 4 倍；
- 页面本身没有横向溢出（`scrollWidth=509`，`innerWidth=524`），说明是列宽挤压，不是整体布局崩坏。

**建议**

- 状态列设 `white-space: nowrap` 和最小宽度；
- 标题列 `word-break: break-word` + 最多两行省略，或点击展开；
- 窄屏把表格切成卡片式布局（标题一行、状态与时间一行）。

## 5. 建议的修复顺序

1. **B01 + N01**：一个让上传完全不可用，一个让回答不可信，都是 P0。B01 改动小，可以先合；N01 需要补停用词、改覆盖率、加回归用例，建议单独一个 change。

3. **B04 + B05 + B07**：引用原文、四态、材料生命周期，三者可以合并成一个“可核验”批次。
4. **N03 / N04 / N05 / N06**：引用编号校验、HTTP 契约、严格 JSON、错误日志，工作量都不大，适合作为同一批“契约收口”。
5. **B08 / B09 / B10 / B11 / B12**：历史、规模、限流、异步索引、超时，属于下一阶段。
6. **N02 / N07**：标题与窄屏排版，随 B03 / B14 一起做。
