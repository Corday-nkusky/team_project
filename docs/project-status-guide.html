01

先建立一页结论

项目状态不是“好 / 不好”一个标签，而是代码、验证、运行和流程四个维度。

CampusClaw 当前已经实现一条可运行的核心垂直切片：登录与班级隔离、教师上传材料、索引、材料全文阅读、学生检索问答、SSE 流式输出、引用回看与无依据拒答。它还不是 README 描绘的全部“教学闭环”成品。2026-11-01 当前分支实测中，完整质量门禁（含 OpenSpec 与 Go 接口 e2e）全部通过；新前端已构建进生产容器，/health 返回 200，MySQL 与 Qdrant 正常，真实兼容网关已启用（chat 与 embeddings），Go 接口 e2e 为 73 / 73、浏览器 e2e 为 51 / 51。Windows 换行导致的 gofmt 红项已通过仓库级 LF 属性稳定修复；前端重设计、换行治理与材料阅读已提交到 feat/workspace-material-reader 分支与 PR #3，但尚未评审、合并和归档；本轮的 add-llm-gateway change 已提交为 PR #4（stacked on PR #3），同样尚未评审、合并和归档。

你真正要掌握的五个问题

  1. 产品：为谁解决什么问题？
  2. 范围：当前代码实际做到了哪一步？
  3. 健康：当前这次检查是否真的通过？
  4. 流程：哪些变更已合并，哪些证据未闭环？
  5. 决策：下一步由哪个风险或 Requirement 驱动？

不要踩的四个认知陷阱

  • README 写到，不等于已经实现。
  • 历史上全绿，不等于当前仍全绿。
  • /health 返回 200，不等于业务 e2e 全通过。
  • PR 已合并，不等于 DoD、评审记录和归档都完成。

03

沿一次请求看懂业务与架构

先理解数据怎样流动，再看包名；这样不会被目录结构淹没。

用户视角：一条核心链路

01登录识别身份账号口令 → 双令牌；角色与班级进入鉴权上下文。
02教师上传材料校验标题、UTF-8、类型和 32 MiB 边界。
03切片并索引原文入库；切片进入本班检索，状态 ready / failed。
04学生本班提问class_id 同时约束数据库与向量检索。
05生成流式回答模型或抽取式降级；SSE 区分完成、中断与降级。
06引用与记录[n] 对应真实切片；问答与审计留痕，无依据则明说。

权限判断先于功能判断

教师能上传与重索引，学生只能查看材料原文和提问；所有资源都先限定本班。跨班返回 403 / 404，不能通过响应差异泄漏资源是否存在。

所以“学生能否读某份材料”不是前端隐藏按钮的问题，而是后端每个查询都必须带 class_id。

AI 的核心承诺不是“会回答”

而是“只依据本班 ready 材料回答”。命中时引用可回看；无依据时固定返回“资料中未找到相关内容”；材料文本被当作数据而不是指令。

没有模型密钥时使用抽取式降级，这是设计能力，不应误判成服务故障。

技术视角：同源单端口与单向分层

04

用证据层级判断“现在”

最重要的习惯：给每个结论贴上来源与时间。

当前实测

你刚运行的命令、退出码、响应与时间；优先级最高。

当前代码与规约

路由、页面、主 spec、活动 change；说明“现在是什么”。

历史验收记录

tasks、verification、独立报告；说明“当时验证过什么”。

愿景与建议

README 后续模块、proposal Non-goals；说明方向，不证明完成。

推荐状态词：当前实测通过 历史通过 待复验 当前失败 未实现 / 非目标。避免一律写“已完成”。

05

一条固定巡检路线

每次汇报、继续开发或接手项目前按同一顺序走。前 1–3 步不需要 Docker；第 4–5 步等服务启动后做。

0 / 6本次巡检进度（只用于当前页面，不会修改仓库）

  1. 看 Git：我正在基于什么工作？

    git status --short --branch
git log -5 --oneline --decorate

    判读：当前分支是否落后远端？未提交的是自己的改动、他人文件还是生成物？最近提交对应哪个 change / PR？

  2. 看活动 change：正在做什么，什么没做完？

    打开 openspec/changes/ 中未归档目录，先读 proposal 的 Why / Non-goals，再读 tasks 的未勾项和“实测”。

    npx --yes @fission-ai/openspec@latest validate --all --strict

    判读：规约通过只说明结构有效；还要检查主 spec、实现和 e2e 是否对应。

  3. 跑离线门禁：代码是否达到提交基线？

    GO_BIN=/d/tools/go/bin/go.exe node scripts/quality-gate.mjs --with-spec

    判读：以最终退出码判定，不只看某几个 ✓。失败时先区分格式 / 分层 / 密钥 / 构建 / 单测 / spec，不重跑掩盖问题。

  4. 看运行态：依赖是否真实可用？

    以下命令会生成或修复本机 deploy/.env 并启动容器；在你准备启动 Docker 后执行。

    node scripts/up.mjs
curl -sS --noproxy '*' http://127.0.0.1:8080/health

    判读：200 且 deps 全 ok 只说明运行依赖健康；503 时看具体依赖。llm.enabled=false 表示抽取式模式，不是错误；enabled=true 只证明配置完整并暴露模型名，不证明网关可达，仍需上传到引用的全链路实测。响应不应含密钥或连接串。

  5. 跑端到端：核心承诺是否仍成立？

    服务与依赖就绪后，在仓库根目录加载本机配置，把宿主机连接地址覆盖到当前命令，再运行 Go 与浏览器 e2e：

    set -a; source deploy/.env; set +a
export MYSQL_HOST=127.0.0.1 MYSQL_PORT=13306 QDRANT_URL=http://127.0.0.1:6333
GO_BIN=/d/tools/go/bin/go.exe node scripts/quality-gate.mjs --with-e2e
    node scripts/e2e-ui.mjs

    判读：分别记录 Go e2e、浏览器 e2e 与总门禁结果，不能把不同结论混成一句。重点看班级隔离、无依据、引用、材料全文阅读的加载 / 错误 / 空态、键盘操作、流中断、上传边界与学生权限视图。不要打印或公开本机密钥。

  6. 回写证据：别人能否复现我的结论？

    把命令、日期、提交号、结果写进对应 tasks / 验收记录；未执行就明确写“待复验”。有真实评审再更新评审记录；按流程归档 change。

    判读：不代填、不代签、不为了好看把历史数字改成当前数字。

06

常见信号，应该怎样解释

掌握项目不是靠记住命令，而是知道每个信号能证明什么、不能证明什么。

观察到的信号可以得出的结论不能据此声称 / 下一步
go test 全通过当前单元测试覆盖的逻辑通过。不能替代真实数据库、Qdrant、浏览器与 SSE e2e。
只有 gofmt 失败总门禁仍失败；构建和单测可在本次独立通过。不能忽略退出码。先看 gofmt -d 与 git ls-files --eol，再治理换行。
OpenSpec strict 通过规约结构与严格校验通过。不能证明场景已经实现或测试映射完整。
/health 200服务可响应，当前 MySQL / Qdrant 探活正常。不能证明登录、上传、检索、引用等全业务正常；继续 e2e。
/health 503至少一个依赖不健康，响应会指出 deps。不要只看“服务挂了”；定位具体依赖，恢复后再探活。
llm.enabled=false当前是零密钥抽取式降级模式。不是模型故障；若要验证模型与向量路，需另配声明的兼容网关。
llm.enabled=true网关配置完整，健康响应暴露当前 chat / embed 模型名。不能证明网关可达或索引已有向量；继续跑上传、索引、提问全链路与 verify-llm.mjs。
PR 已合并对应代码进入目标分支。不能自动证明 tasks、真实评审、文档与归档全部闭环。
历史记录 63 / 32 全绿对应日期与环境曾通过这些 e2e。不能当作今天的实测；服务启动后重跑并记录新结果。

遇到矛盾证据时，这样处理

README 写了很多功能，但界面找不到
以当前路由、页面、主规约和已归档 change 判断实现范围。README 中的“目标 / 后续轮次”保留为愿景，不改写成已实现。
tasks 写全绿，但我刚跑出失败
当前实测优先。记录当前提交、环境、命令和失败项；历史记录不删除，因为它描述的是另一时点。先定位差异，再决定是代码回归还是环境问题。
PR 已有审批，但仓库评审表仍为空
先核对真实 PR 审批与团队约定，再把可验证的评审事实回填到指定记录。不能虚构签字，也不必为了形式重复做一次没有必要的评审。
偶发失败，重跑一次过了
不能把它当作解决。保留第一次输出、实际值和期望值，定位根因；规范明确禁止用重试掩盖偶发失败。

真实兼容网关已验证：llm.enabled=true、上传后 ready、Qdrant 存在向量点、问答有增量与引用且无降级；嵌入失败与恢复演练也通过。变更已提交为 stacked PR #4，待 PR #3 合并后评审合入 main 并归档。注意：启用前已存在的材料只有关键词可用，需按 README 删除旧集合并重索引全部材料后才有向量。

P1
核对并补齐真实流程记录

检查此前 PR 审批事实、tasks、peer-review 与 change 归档之间的关系；按真实事实闭环，不代签、不补造过程。

P2
再选择下一个产品或架构 change

从历史、规模、限流、异步索引或 README 后续模块中选题。先回答价值三问、失败路径与非目标，再写实现任务。

判断优先级的方法：先问“不处理会怎样”。门禁红会阻断交付；无依据误判会破坏核心信任；材料内搜索或 Markdown 体验则通常可以后排。严重度来自影响，不来自修改难易。
08
