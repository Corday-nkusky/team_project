上台前，只准备一条主线

目标不是展示“规则很多”，而是让全班亲眼看到：规则能拦住一次真实违规。

一句话策略：一个案例、一个门禁、一次失败、一次恢复。不要现场追加第二个故障，不要逐条朗读八份规范。

课前 3 分钟检查

提前打开的仓库位置

01

10 分钟现场路线

每一段都有“打开哪里、说什么、做到什么程度”。讲稿可直接照读，熟悉后换成自己的表达。

00:00
— 01:00

开场：我们如何解决“规范写了没人用”

打开仓库根目录，不急着翻文件。

老师、同学们好。我们组这次想分享的，不是“写了八份规则”，而是我们怎么让这些规则不只靠自觉。AI 和人类一起写代码时，规范最容易变成文档摆设，所以我们给每份规则都补了检查方式、违规处理和一次有效性验证。接下来我会故意制造一次分层违规，让大家看看门禁是不是真的能拦住。

01:00
— 02:30

总入口：规范怎样进入开发过程

↗AGENTS.md指到第一、二、七、八、十节即可，不滚动朗读全文。

这个文件是所有成员和 AI 工具的共同入口。每次改动先写 OpenSpec，场景必须能判定；实现后跑统一门禁；最后还要同伴评审。也就是说，规范同时约束需求、代码、测试和交付，不是只管代码风格。

手势：指向“规范不是建议”和“变更流程（不可跳过）”。

02:30
— 04:00

解剖一份规则：四层闭环

↗.qoder/rules/02-backend.md重点看第 7–15、17–21、23–26、28–30 行。

以后端规范为例。第一层是可执行的规则，比如传输层不能直接接触向量库；第二层是检查方式，对应分层脚本和 Go 工具链；第三层是违规处理，失败就阻断合并；第四层最重要——有效性验证，主动放一个反向依赖，确认检查不是永远说“通过”。

04:00
— 07:00

高潮：故意违规 → 门禁失败 → 删除恢复

按下一节的五个步骤操作。看到失败后只解释一条报错，不展开源码。

现在我不改任何业务逻辑，只临时增加一个探针文件，让 httpapi 直接引用 qdrant。按照规范，这应该被拦截。大家看，检查退出失败，而且准确指出了文件和原因。这次失败，恰恰证明门禁成功。现在删除探针，再跑一次，恢复通过。

07:00
— 08:30

从一个脚本到完整证据链

↗scripts/quality-gate.mjs配置样例、分层、密钥、gofmt、build、vet、test。↗verification.md 第四节历史实测：分层与密钥演练、恢复结果。

单点脚本还会被收进统一质量门禁。更重要的是，演练结果会写进验收记录：做了什么、预期什么、实际是什么、最后有没有恢复。这样别人不需要相信我们的口头保证，可以复现证据。

08:30
— 10:00

收尾：门禁有效，但门禁不是全部

我们的收获有三点。第一，规则要写成能检查的契约；第二，检查本身也要被测试；第三，失败之后必须有明确处置和恢复。我们也承认门禁不是万能的：产品价值、检索是否真正可信、真实依赖下的端到端行为，还需要场景测试和同伴评审。对我们来说，工程规范不是让开发变慢，而是让信任变得可验证。谢谢大家。

最后一句说完就停。不要再补充新例子，把剩余时间交给提问。

02

现场演示操作卡

安全边界：只新增并删除一个以下划线开头的 Go 探针；不改业务文件，不需要 Docker，不接触模型密钥。

为什么用 _probe_layering.go？ Go 构建工具会忽略下划线开头的文件，而分层脚本会扫描所有 .go 文件。因此它能隔离地验证分层门禁，不影响业务二进制。
  1. 先证明当前通过。在仓库根目录运行：
    node scripts/check-layering.mjs

    预期：输出“分层依赖检查通过”，退出码 0。若课前已是失败状态，不现场造第二个问题，直接改用历史证据方案。

  2. 新建探针文件。路径必须是：
    backend/internal/httpapi/_probe_layering.go

    内容只有两行：

    package httpapi

import _ "github.com/Corday-nkusky/team_project/backend/internal/qdrant"
  3. 再次运行同一命令。
    node scripts/check-layering.mjs
    预期失败，且这就是演示成功：
    httpapi 不得直接引用 internal/qdrant，应经 qa 间接调用
    进程退出码为 1，并指名 _probe_layering.go。
  4. 解释“为什么拦”，只说一句。传输层负责解析、鉴权与响应；向量和模型访问必须经过应用层 qa，这样业务编排不会散落到 handler。
  5. 立即删除探针并复跑。确认文件已不存在，再运行：
    node scripts/check-layering.mjs

    预期恢复通过。可用 git status --short 确认列表中没有 _probe_layering.go；仓库里其他已有文档不属于本次探针。

绝对不要：为了让报错“更明显”而修改多个文件；不要演示真实密钥泄漏；不要在失败后跳过还原；不要把当前总门禁是否全绿与这次单点分层演示混为一谈。
03

现场不顺，也有 30 秒救场方案

救场的目标不是证明你操作熟练，而是保住论证完整性。

命令本身失败

先读第一行错误。若是环境或既有工作区问题，不现场排查；打开 verification.md 第四节。

说：“现场环境占用了时间，我们直接看已记录的同一演练；关键仍是它同时保存了失败和恢复证据。”

时间已超过 07:00

立即删除探针并复跑。省略质量门禁源码，只打开验证记录。

说：“脚本细节大家可以课后看，我只保留结论：失败可定位、恢复可复验、过程有记录。”

探针没有触发失败

检查路径是否在 backend/internal/httpapi、扩展名是否为 .go、import 是否完整。最多纠正一次。

还不触发：坦诚说这本身暴露了门禁盲区，停止演示，记录为待修问题；不要假装成功。

表达纪律：不把历史通过说成“今天刚刚通过”；不把“代码合并”说成“所有完成定义已闭环”。这两句话反而会让你们对证据的理解更可信。
04

5 分钟问答应答库

每题控制在 25–40 秒。先给结论，再举一个仓库证据，最后承认边界。

规则这么多，会不会拖慢开发？成本

会有固定成本，但它替代的是返工和争论。小团队不需要每次都重读全部规则；入口文件告诉你要走 change、门禁和评审，细则只在涉及对应领域时查阅。真正省时间的是错误在本地、合并前就被发现，而不是演示或联调时才暴露。

AI 真的会遵守这些规范吗？AI 协作

不能把“写给它看”等同于“它一定遵守”。所以 AGENTS 只是发现入口，脚本和退出码才是硬约束。规范负责让要求可发现，门禁负责让违规可观察，评审负责处理自动检查覆盖不到的判断。

为什么要故意违规？正常测试通过不就够了？核心

因为“没有报错”可能只是“没有检查到”。正常样本通过只能证明门禁不拦正确代码，不能证明它会拦错误代码。故意违规相当于给门禁本身补一个负向测试：既要会放行，也要会拒绝。

故意违规会不会把仓库或数据弄坏？安全

关键是选择隔离、可逆、无外部副作用的探针。这次只新增下划线开头的 Go 文件，不进入业务构建，不启动服务、不碰数据库；验证后删除并复跑。真实密钥泄漏、破坏性迁移不适合课堂现场演练，应只用历史受控记录说明。

全部门禁通过，是否说明项目质量没问题？边界

不能。离线门禁主要保证结构、配置卫生、格式、构建和单元测试；真实 MySQL、Qdrant、浏览器和 SSE 行为还要靠端到端测试。产品是否有价值、规则是否合理、回答是否真的可信，仍需要独立走查和人的评审。

为什么不让 CI 直接做，而要保留本地脚本？工程

同一套脚本本地和 CI 都能跑，反馈才一致。本地门禁把问题拦在提交前，CI 再做独立复验；脚本进仓库后，检查逻辑本身也能被评审和版本追踪，而不是藏在某个平台配置里。

新成员怎样开始，不会被规范吓住？上手

从一条真实改动走一遍，而不是背规范。先看 AGENTS 的项目一句话和变更流程，再复制一个相近 change 的四件套；实现后按 tasks 的 verify 执行，最后跑统一门禁。三个技能把新增接口、质量检查和从零启动做成了可复用流程。

你们现在的流程是否已经全部做到位？坦诚

还不能这样概括。核心功能和修复已经落地，但“代码合并”不等于完成定义全部满足；评审记录、任务勾选和 change 归档仍要持续闭环。规范的价值也包括让这些缺口可见，而不是把项目包装成永远全绿。

下一步最该改进什么？演进

优先让规范持续有效，而不是继续增加条目。定期抽查已归档场景是否仍对应 e2e，检查最近合并是否都有门禁与评审证据，并对跨平台换行等环境问题做稳定化处理。只有规则被反复使用、违规确实被发现，规范体系才算活着。

05

带上台的六句提词

忘词时只看这里。每句对应一个动作，不影响主线。

1　“我们分享的不是规则数量，而是规则如何被证明有效。”
2　打开 AGENTS：“需求、代码、测试和交付走同一条契约。”
3　打开后端规范：“规则、检查、处置、有效性验证，四层闭环。”
4　制造探针：“现在这条错误应该被拦住——失败就是门禁成功。”
5　删除复跑：“可定位、可恢复、可复验，才值得信任。”
6　收尾：“自动门禁不是全部；端到端和人的评审仍然必要。”
最后检查：探针已删除 · 分层检查恢复通过 · 没有展示任何本机 .env 或真实令牌 · 没有承诺“项目所有方面都全绿”。
