01

三层，各管一件事

模型每次输出是概率采样。不改模型，改它周围的环境。三层不是并列的能力清单，是三种不同的约束方式。

第一层 · 注入：它知不知道规矩

AGENTS.md 常驻会话，.qoder/rules/ 八份细则由 Qoder 直接注入，三个技能按需调用。

规则本身是控制手段。对比一句空话和一句可执行的：代码要规范 对模型没有信息量；JWT_SECRET 必须 ≥32 字符且非示例值 可以直接照做。指令越具体，输出方差越小。

规则不是一段话，是四段式。翻 02-backend.md：第 7–15 行九条规则，17–21 检查方式，23–26 违规怎么处置，28–30 怎么验证检查本身。

上限：注入依赖模型真的去读，读了也可能不照做；换个只认 AGENTS 的工具，细则就得自己按索引翻（降级，不是失效）。

第二层 · 流程：它做没做

一次大输出越长越容易跑偏，所以拆步：proposal（为什么改）/ design（怎么改）/ specs（改完什么行为）/ tasks（分几步）。

场景必须可判定。runtime-baseline R8.2：GIVEN 除 JWT_SECRET 外齐全，WHEN 启动，THEN 非零码退出。写不出 THEN，说明需求没想清。R8 六条里五条是失败路径。

实测写回，比“已完成”有力。add-rag-eval tasks 5.2 的实测记着：“Git Bash 下会因 GOCACHE 未传递而报错，需显式给”。这种细节编不出来。

最能讲的一个案例：tasks 3.3。初版自动生成的 B 类问句 R@4 = 1.00，看着满分；一查是送分题——问句和答案句词面几乎重合。于是改成留空，不再输出误导性满分。满分反而暴露了问题，这是门禁永远抓不到、只有实测才能抓住的东西。

上限：人能跳步，verify 写了不跑；流程只约束愿意照做的人。

第三层 · 门禁：它交的东西合不合格

一条命令七项：配置样例、分层、密钥、gofmt、build、vet、test，退出码决定放不放行。

层级表是数据，不是文档。check-layering.mjs 第 19 行：internal/qa 是层 1、httpapi 是层 2。真实例子：新增 cmd/rageval 入口时没登记，脚本直接失败——加一个包，必须显式做一次架构决策。

判定是一个 if。第 100–104 行：命中禁止集合就往违规列表推一条。规则在这不是口号，是代码。

白名单而不是一刀切。httpapi 可以用 store，但只许 4 个文件。规则没假装能禁绝一切，而是把豁免枚举出来——想加豁免，改脚本、过评审。

上限：只判结构。并发、事务、越权只在特定时序下暴露，静态检查一句话都说不出来。

为什么必须叠：只有注入，模型可能没读或不照做；只有流程，人能跳步；只有门禁，覆盖窄。叠起来的效果是错误被发现时最便宜——注入少犯错，流程让错在写代码前暴露，门禁让漏网的必然现形。
02

规范写成了什么：可判定的条款

八份细则合计 255 行，比一份 README 还短。因为每条只写一件事：什么行为可判真假、谁来判、违反了什么后果。

判据：一条规则如果写成形容词，它就不是规则。“代码要规范”“注意安全”无法判定真假，模型无从服从，评审也没法说“你违反了第几条”。八份细则的共同写法是给数字、集合、状态机——不是文风偏好，是让规则具备可执行性。

人

数字不是口味，是约束

32 MiB 上传（spec R3.4）：请求体上限是它再 +1 MiB（maxUploadBytes + 1<<20），预留给 JSON 转义与 multipart 边界，避免正文刚好 32 MiB 时被误伤。

它必须和列容量成对：早期 content 是 MEDIUMTEXT（16 MiB），17 MiB 的上传能过接口检查，却在写库时报 500。修法不是调小上限，是把列扩到 LONGTEXT 与上限对齐——见 db.go 的 migrateMaterialContent。

1 MiB 问答请求：一个问题加检索上下文远小于此，超限基本等于攻击或前端 bug。

13306 端口：避开宿主机 3306，别人本机的 MySQL 和本项目可以共存。

写规范时先问“这个数字由什么决定”。答不出来，说明这个数字是拍的——而拍出来的数字和别处的约束一定会打架。

违规处理分级别，不写“严肃处理”

密钥泄漏：立即轮换、吊销相关令牌、回滚提交、24 小时内补事故记录。

越权或数据泄漏：按 P0，先止血再修复，并补对应负向 e2e。

无断言的“测试”：视为未测试，评审直接打回。

破坏性迁移：阻断合并；已执行则按备份恢复并补评审。

共同点：每条都写明谁做、多久内、做完补什么，而不是“加强重视”。

03

一个改动怎么走完全程

以 2026-11-03-add-rag-eval 为例，八步，每步都有可核对的产物。流程的价值不是仪式，是让“想清楚”发生在“写代码”之前。

  1. proposal：先回答为什么。价值三问 + 非目标。原文写着“没有分项指标，任何一次调整都是盲调”——这句话既是立项理由，也是后来验收的口径。
  2. design：把取舍写下来。切片粒度 × 关键词/向量/融合/RRF 的横评方案，以及降级路径：无模型网关时不产生假的融合分数。
  3. specs：把行为写成可判定的场景。Requirement + GIVEN/WHEN/THEN，每个 Requirement 至少一条失败路径。openspec validate --all --strict 实测输出 8 passed, 0 failed。
  4. tasks：拆到能判定。每条带 verify:。2.2 的验收是“check-layering.mjs 通过且不报未登记”——把一个架构决策变成一条任务，跑不过就不许勾。
  5. 实现：小步改，先证明没改坏。同源改造把 EvidenceOK 提到 internal/retrieval，验收条件写的是 qa_test.go 一行不改仍全绿——证明重构没有改变在线判定行为。
  6. 实测写回：把命令和输出贴进 tasks。3.1 记着“材料 98 条、题目 207 条（可评测 89）”；5.2 记着 Git Bash 下 GOCACHE 未传递会报错。这些数字只可能来自真跑。
  7. e2e：退出码即判定。quality-gate.mjs --with-e2e，任一失败退出 1；接口断言与浏览器走查都在同一条命令里。
  8. 归档：让主规约追上实现。openspec archive → 变更目录移入 changes/archive/，主规约同步；提交信息引用编号（feat(R8)、docs(R12)）。

流程真正拦住的两件事

一、想不清就写不出来。THEN 写不出来，说明需求本身含糊，这时候改代码是浪费。失败路径那一栏空着，等于承认只想了顺利情况。

二、声称完成但没做。tasks 要求贴命令与真实输出。模型可以编造描述，编不出一个真跑过的输出；贴错了复核时会被发现。

分支模型与它当前的代价

main 受保护（PR + 1 人评审），功能走 feat/*。PR #2（独立走查缺陷修复）已合并；PR #3（工作台与材料阅读）open；PR #4（LLM 网关）叠在 #3 之上。

叠 PR 的真实代价：scripts/verify-llm.mjs 只存在于 feat/llm-gateway，main 和 feat/workspace-material-reader 上都没有。分支一旦漂移，文档和脚本就对不上——这是协作成本，不是技术债。

流程里最容易被低估的一步是第 6 步。前五步都能由工具检查格式，只有“实测写回”要求人把外部世界的结果搬进文档。B 类问句 R@4 = 1.00 那个案例就是在这里被发现的：满分不是成绩，是题目太容易的信号。
04

团队怎么协作：留痕、独立、可复现

三人加各自的编码 Agent。协作要解决的不是“谁负责哪块”，而是“凭什么信对方说做完了”。

分工按 change，不按文件

切文件会产生大量并行冲突（同一个 main.go 被三个人改）；按 change 切，每个改动自带规约、任务和验收，边界由 spec 划而不是由目录划。

Agent 有硬边界

team-deployment.md 给队友的编码 Agent 定了 7 条：按章执行不跳步、只改本机 deploy/.env、不执行 commit/push、不回显密钥、首次构建可能超 10 分钟不要中断、失败先停不要随机重试、结果回传。

判定必须留痕

peer-review.md 规定评审对象（tag）、复现命令、15 项清单、P0/P1/P2 分级、结论与签字栏。“通过”不是一句话，是一张能复查的表。

独立走查：作者自测替代不了的那一步

2026-10-30 那次走查不跑仓库自带的 e2e，而是用三条独立路径重验：Node fetch 手工按空行解 SSE 帧；起一个假的 OpenAI 兼容网关，支持 [CUT] / [EOF] / [EMPTY] / [500] / [CITE9] / [SLOW] 六种故障模式；浏览器走真实文件选择、真实登录、真实“停止”按钮。

结果抓到一个 P0，而且是自己那套测试抓不到的。“如何 / 都是 / 什么”这类常见双字词就能越过相关性门槛：问“如何在家做红烧肉”，系统返回《动物行为学》并标记 no_evidence=false。根因在 retrieval.go:164 的 tokenize——相邻汉字组合全部标 strong，没有停用词表。对照组“紫罗兰色的大象在跳舞”反而正确拒答，说明这不是模型幻觉，是检索判定错误。

同一份报告还修正了原计划的一处事实错误：17 MiB 上传不是“静默截断后 201”，而是 500 落库失败，因为 content 列当时是 MEDIUMTEXT（16 MiB 上限）。这条只有走独立路径才会暴露——仓库自带的 e2e 断言的是它自己认为的边界。

修法值得单独讲：不是把上传上限调小，也不是截断，而是把列扩成 LONGTEXT 与 32 MiB 对齐。迁移函数先查 information_schema 判断列类型，已是 longtext 就直接返回——重复执行安全，正好落地 07 数据规范那条“幂等迁移”。缺陷由 PR #2 修复并合入 main。

05

有效性验证证明什么，不证明什么

这一节回答两个问题：凭什么信这个门禁不是摆设？以及，它凭什么不是同义反复？

为什么需要演练：失败分支是死代码

正常提交永远走“通过”那条路，exit 1 那几行从来没被执行过。安静的房间证明不了烟雾报警器有效——可能它没接线、没电池、或者根本没装。得划一根火柴。

所以每份规则最后一节都留了故意违规演练：造一个违规，确认门禁真的失败，再还原，过程记进 verification.md。目前有两条：分层（加 _probe_layering.go import qdrant，预期失败，实际 exit=1 并指名文件）、密钥（compose 里加 :- 回落，预期失败，实际报“不得提供回落默认值”），第三条是还原复查。

它能排除的三种“哑门禁”

失效形态具体长什么样
根本不响扫目录时排除了子目录、文件名大小写写错、正则只匹配单行 import 漏了括号块——对真实违规视而不见。
响错方向条件写反（少一个 !）、白名单放太宽把所有文件都放进去——永远说通过，还显得很勤快。
响了没人听见推入了违规列表、打印了红字，却没执行 process.exit(1)——终端一片红，退出码 0，CI 照样绿。

三种都在正常开发里活得很久，因为正常代码永远触发不到它们。所以“一直通过”这件事没有信息量。

同义反复：成立，但分两种

弱版本（真同义反复）：样例是照着脚本的 if 分支反推的——“脚本禁 httpapi→qdrant，我就造 httpapi→qdrant”。这只是在验证代码和自己一致，信息量为零。

强版本（有信息量）：样例从规则文本独立推演。02-backend 第 1 条写的是“禁止反向依赖”，由此能推出至少三种形态：httpapi 直连 qdrant、qa 反向 import httpapi、store import qa。脚本里没有为三种各写特判，而是用通用层级比较统一判定——两条独立路径撞上了，才说明有鉴别力。

判据只有一条：样例是否独立于实现。样例来自规则文本 → 有信息量；样例是脚本分支的镜像 → 同义反复。

实际缺口（主动说，别等被问）

性质证据说明
敏感度：已知违规被抓部分只练了两类形态（分层、密钥），各一次。
特异度：合法代码不被误杀间接门禁全绿、13 包 25 条引用通过；但“通过”也可能是检查太松。
完备性：形态全覆盖没有别名导入、中间包间接引用、白名单文件塞业务逻辑，都没测过。
纯约定规则空白02-backend 的“错误不吞”“context 贯穿”“幂等”没有机器检查，也就没有演练。
长期有效快照两次演练都在 2026-10-28，之后没再跑；也不是回归测试。

另一类证据（更容易被忽略）：verification.md 第五节做过一次无上下文只读代理抽查——只给仓库路径和“新增一个接口按规范怎么做”，看它能不能自己找到规则并答对。它引用了 AGENTS + 4 份 rules + 2 个 skills，答案与规范一致。这条证明的不是门禁会响，而是规范可发现、可执行，而且不是作者自证。

06

覆盖不全怎么补

四步，按性价比排序。第一步是纯文档，最后一步才需要动 CI。

做法具体动作解决什么
1. 覆盖矩阵
半天		把“检查项 × 违规形态”列成表贴进 verification.md：分层至少 4 形态（直连禁止包 / 反向上行 / 未登记新包 / 白名单外用 store），密钥至少 4 形态（私钥块 / sk- / compose 回落 / 代码硬编码）。把“覆盖不全”从感觉变成空格子，缺口可数。

可选		纯约定规则做启发式扫描（handler 里出现 SQL 关键字 → 提示人工确认），并写进 peer-review.md 固定勾选项；在 verification.md 明写“无自动化覆盖”。让“没有检查”这件事可见，而不是空白看起来像通过。
5. 拦截率
持续		记录一段时间内门禁失败次数与原因分类。三个月零失败 → 要么团队完美，要么门禁哑了，强制重跑演练。解决“快照”问题，让有效性随时间可复查。
做完第 2 步，体系的样子就变了：不再是“某天演练过一次”，而是“任何人任何时候跑一条命令，都能确认门禁还活着、且只拦该拦的”。

08

会被追问的

只留真正会被问、且正文没答的。一句结论 + 一个证据。

这套和“提示词工程”有什么区别？概念

提示词管一次对话怎么说，harness 管整个环境。哪些规则常驻、改动走什么流程、产出由谁判定——三件事都不在提示词里。前者影响一次采样，后者让错误在流程里被强制暴露。

规则注入是 Qoder 自动做的，换个工具不就废了？跨工具

会降级，不会失效。别的工具只自动读 AGENTS.md，细则按索引自己翻。但流程写在 openspec/、门禁跑在 scripts/，这两层不依赖工具。

门禁又不改模型，凭什么让输出稳定？核心

它让不稳定变得可见且便宜。单次输出仍随机，但错误必然被拦，重做成本只是一次生成。稳定来自“生成—校验—重做”的循环，不来自模型。

既然有门禁，为什么还要人工评审？分工

门禁只判它能扫的东西。并发、事务、越权、错误吞没这四类，静态检查说不出来；而且 02-backend 里“错误不吞”“context 贯穿”“幂等”三条本来就没有机器检查。这些只能人看。

没有 CI，门禁靠人跑，那不等于没有？诚实

目前是纪律强制，不是机器强制。仓库里没有 CI 配置，执行点是提交前跑 quality-gate.mjs + 同伴评审核对。补 CI 是一行配置的事，但没做就是没做。

三个人具体怎么分工的？协作

按 change 切，不按文件切。每个改动自带 proposal、specs、tasks 和验收，边界由规约划，谁在改什么从 change 目录就能看出来。角色上分三种：作者、评审人、独立走查者。诚实补一句：从提交记录看主力集中在两个账号，第三名成员参与部署验证与协作者权限，并行度其实不高——机制齐了，实际利用率不够。

评审没签字，是不是等于没完成？DoD

是，按你们自己的规定就是不成立。peer-review.md 第一行写着“未签署……不满足完成定义”，AGENTS.md 第八节也写“自审不能替代同伴评审”。所以对外只能说“机制已建立、这一环待闭环”，不能说“已完成”。

独立走查不算重复劳动吗？验证

不算，因为它绕开的是同一套假设。自带 e2e 断言的是作者认为的边界，边界本身错了它抓不到。那次走查不跑 e2e，改用假网关制造六种故障、手工解 SSE 帧、浏览器点真实按钮，才抓到 P0，并纠正了“17 MiB 静默截断”这个错误前提。代价是一天，收益是避免把错误前提写进后续所有修法。

你们现在已经做到哪一步了？坦诚

三层都有雏形，三层都有缺口。注入受限于工具；流程里 tasks 勾选未全部闭环；门禁没有 CI、只覆盖两类演练形态；同伴评审记录至今未签署。这些缺口在 verification.md 里都写着，不是现在才承认。
