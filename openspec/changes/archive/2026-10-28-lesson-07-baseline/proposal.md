# Proposal

## Why

第 7 课要求小组项目在写业务代码之前完成四件事：建仓库、定规约、立规范、落骨架。本仓在 2026-10-14 已完成第一轮垂直切片，但当时的交付形态是「代码先行」：

- 仓库有 README 与 `.gitignore`，但首提交含选题 PDF、`.gitignore` 与首批代码同批入库，`main` 无保护；
- OpenSpec 有四件套并通过校验，但场景缺「前置条件」，也没有能力↔场景对照表；
- 五类工程规范没有落成文件，Harness 读不到任何项目级规则或技能；
- 骨架能启动，但配置有默认值、日志是文本、`/health` 缺版本与时间，也没有骨架标签与验证记录。

这不是功能问题，是基线问题：后面每课都要在这条基线上增量交付，缺了规范与可复现骨架，新增功能会继续按个人习惯分叉。本次变更把第 7 课的基线补齐，不改业务行为。

价值三问：

- **给谁用**：本组三人；后续接手者；按 README 从零启动的评审者。
- **解决什么问题**：把「怎么做、怎么查、怎么算完成」从会话记忆变成仓库文件，避免换人、换会话后做法漂移。
- **比现有做法好在哪**：同一份规则可被 Harness 每次读到；一条质量门禁可复现地判定；骨架标签提供回归对照点，而不是靠口头约定。

## What Changes

本次变更只做基线，不新增业务能力：

1. **规约**：新增 `runtime-baseline` 能力，覆盖配置外置与启动校验、健康检查、结构化日志与请求标识；补全既有主规约场景的前置条件（表述修订，不改变行为），并给出能力↔场景对照表。
2. **规范**：新增根 `AGENTS.md`、`.qoder/rules/` 下五类规范与三类补充规范、`.qoder/skills/` 下三个按场景执行的技能；每条规范写检查方式与违反处理。
3. **骨架**：配置必需项缺失即启动失败；日志改为单行 JSON 并带 request ID；`/health` 增加 version/time；新增分层与密钥门禁脚本；更新 Compose、Dockerfile、`.env.example` 与 README。
4. **交付**：补 `docs/lesson-07/` 验证记录与交叉评审模板；归档本变更并打 `v0.0.1-skeleton`。

## Capabilities

### New Capabilities

- `runtime-baseline`: 运行基线的可判定要求——配置缺失即失败、健康检查可探活、日志可串联且不泄漏敏感信息。

### Modified Capabilities

（无）既有 `auth-upload` 与 `knowledge-retrieval` 的行为不变；只补场景前置条件，属于表述修订。

## Non-goals（本次不做）

| 项 | 性质 | 本次不做，是因为 |
|---|---|---|
| 新增业务功能 | 排期 | 第 7 课只要求基线；业务能力按后续课次增量加入 |
| 重构认证 / 检索 / 问答实现 | 排期 | 本次只补运行基线与规范，避免把基线变更做成大重构 |
| 重写 Git 历史 | 明确不做 | 首提交的 PDF 与 `.gitignore` 时序已是历史；重写会破坏协作与提交哈希，风险高于收益 |
| 公网部署 | 排期 | 部署与运行验证属第 10 课；本次只保证本地一键启动与可复现 |

## Impact

- **代码区域**：`backend/internal/config`、`backend/cmd/server`、`backend/internal/httpapi`、`deploy/`、`scripts/`；前端业务逻辑不动。
- **配置**：部署关键项改为必需；`.env.example` 只保留键名与占位值；Compose 对必需项使用 `:?` 失败。
- **日志**：运行期日志改为单行 JSON；日志字段与 request ID 进入规范。
- **规约**：新增 1 个能力、16 个场景；既有 24 个场景补前置条件。
- **文档**：新增 `docs/lesson-07/` 验证记录与交叉评审模板。
