# Design

## Context

- 本仓 2026-10-14 从零起步，代码零行；三人分工（制定规约 / 开发系统 / 项目验收）。
- 课纲要求完整互联网应用 + 五项 AI 能力 + 规约驱动 + 须公网可访问；**技术栈不限定**。
- 已定：本仓**从零重写**，个人仓 `campusclaw-corday` 只作**问题域参考**，不搬成品。
- 与个人仓的关系：**只借鉴问题域结论**（例如检索为空时先查索引状态、SSE 中间件丢 Flusher 的坑），
  **不复制代码与表结构**。凡借鉴处在对应用任务或代码注释中标注，便于验收组区分「经验」与「本仓设计」。

## Goals / Non-Goals

**Goals:**

- 用一条垂直切片证明「这套组合跑得起来」，并留下可被课纲验收的证据（页面 / 接口 / 失败路径 / 日志）。

**Non-Goals:**

- 本版不做任何业务模块（范围与理由见 `proposal.md` 的 What Changes 与 Non-goals）。

## Decisions

### D1 用「垂直切片」而非「按层推进」

一次只打通**一条**从界面到数据库的完整链路（登录 → 上传 → 问答 → 引用），而不是先做完整个后端再做前端。

**理由**：按层推进时，在两侧都完工前没有任何一条功能能被演示或验收，字段名 / 返回结构 / 错误码不一致
要拖到期末集成才暴露。垂直切片让三条线（前端 / 后端 / 测试）**同一天都有可验收的产出**，
且第一刀就把 SSE、权限、引用这些真坑撞出来。

**代价**：前一两次交付的"功能覆盖面"看起来窄。

### D2 沿用已跑通的组合：Go + MySQL + Qdrant

**理由**：该组合已在本机完整跑通（登录 / 上传 / 检索 / 流式问答），**可行性有实物证据、不需要任何人背书**；
公开仓 README 已如此记载，无需改动。前沿性体现在应用层（检索质量、智能体、MCP），
底座越稳越好——底是地板不是天花板。

**代价**：若将来需要在服务器上自托管推理模型，Go 的生态支持弱于 Python；本版模型走 API，不受影响。

### D3 模型走托管 API，不在服务器上自托管

**理由**：本版目标是打通链路，不是模型部署；API 调用与语言解耦，不引入推理环境。
**代价**：依赖外部服务可用性与密钥；密钥一律外置为环境变量，不进仓库。

### D4 检索：关键词 + 单路向量，不加重排

**理由**：先证明"检索 → 有依据回答 → 引用可回看"这条链成立；重排 / 改写是质量优化，不是链路前提。
**代价**：召回质量弱于加入重排的方案（后续版本按需求评估补上）。

### D5 认证载体：请求头 Bearer token，不用 Cookie + Session

客户端以 `Authorization: Bearer <access token>` 头携带凭证。

**理由**：前后端分离，且本版要求公网可访问；Cookie 方案需额外处理跨域（`SameSite` / `credentials`）
与 CSRF 防护，而 Bearer 方案无 CSRF 面、链路更短。
**代价**：凭证由客户端自行保存与携带，前端需实现「收到 401 → 刷新 → 重放请求」的续期逻辑。

### D6 SSE 流式由后端主动 Flush

**理由**：流式的关键是服务端**边生成边推送**。若中间层（包装 ResponseWriter 的中间件）未透传
`http.Flusher`，客户端会退化为"一次性收到全部"，表现为**假流式**。
**代价**：任何包装 ResponseWriter 的中间件都必须透传 `Flush()`，`tasks.md` 中列为独立验证项。

### D7 审计取「最小可用」而非完整审计体系

**理由**：课纲要求"审计"，本版只需三类动作各留一条可追溯记录即可构成证据。
**代价**：留痕为普通表记录，可被有库权限者修改；完整审计（不可篡改、归档、查询界面）留后续版本。

### D8 登录态为 access + refresh 双令牌，刷新即轮换

access token 短期无状态签发（约 15 分钟）；refresh token 长期有效（约 30 天）、**落库且只存摘要**，
每次换取新 access token 时**轮换**：同时签发新 refresh token，旧 refresh token 立即失效。

**理由**：短 access 把凭证泄漏的可利用窗口压到分钟级；refresh 落库使**登出与吊销成为可能**
（吊销 refresh 即终止该会话的续期能力——这解决了纯无状态方案"签发后无法吊销"的问题）。
**代价**：引入刷新令牌表、轮换逻辑与一次额外请求；前端须实现静默续期；refresh token 走一次网络后
即被轮换，客户端并发刷新需自行串行化（本版以前端模块级互斥控制，列为 tasks 验证项）。

## Risks / Trade-offs

| 风险 / 取舍 | 说明 | 应对 |
|---|---|---|
| access token 有效期内不可吊销 | 见 D5 / D8 | 有效期压到分钟级；登出即吊销 refresh，终止续期能力 |
| 假流式 | 见 D6 | tasks 中列为独立验证项（用 `curl -N` 观察分次到达） |
| 召回质量弱 | 见 D4 | 本版接受；重排列为后续版本的【排期】项 |
| 依赖外部模型 API | 见 D3 | 密钥外置；失败路径在 spec 中有明确响应 |
| 换栈风险 | 见 D2 | 若日后换栈，底座骨架需重写，但 spec（外部行为契约）不受影响 |

**未决（留到对应切片再做决定，不阻塞本版）**：前端组件与状态管理方案、编排框架、可观测方案、评测工具。
