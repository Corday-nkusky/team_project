# 产品设计规范

适用范围：需求、交互、文案、验收标准的提出与变更。

## 规则

1. **价值三问**：每个 change 的 proposal 必须回答「谁的问题 / 不做会怎样 / 做完如何验证」。
2. **场景化需求**：功能一律写成 `Requirement + Scenario`，Scenario 必须含 GIVEN / WHEN / THEN；禁止只写「支持 XX」。
3. **失败优先**：每个 Requirement 至少一条失败或异常路径（拒绝、降级、无依据）。
4. **四态齐全**：页面必须定义加载中、空、错误、正常四种状态；空态给出下一步操作。
5. **非目标显式**：proposal 必须列「不做什么」，防止范围蔓延。
6. **文案即契约**：固定文案（如「资料中未找到相关内容」）以 spec 为准，前后端不得各自改写。
7. **可判定验收**：每条任务的 `verify:` 必须是可执行命令或可观察结果，不写「体验良好」。

## 检查方式

- `npx @fission-ai/openspec@latest validate --all --strict`
- 变更评审时逐条核对 proposal 的价值三问与非目标
- 前端 e2e 覆盖四态中的可自动化部分（空态、错误态、流式态）

## 违规处理

- 缺 GIVEN/失败路径的 change 不予实现，退回补规格。
- 已实现但文案与 spec 不一致：以 spec 为准修复，并在 tasks 记录偏差。

## 有效性验证

每季度抽查一个已归档 change，确认其 Scenario 仍能对应到现有 e2e 断言；对不上的补断言或废止该场景。
